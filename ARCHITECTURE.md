# ARCHITECTURE.md

Гайдлайн по структуре кода для сайта TRENDSETTER. Стек: **Next.js (App Router) + TypeScript + Storyblok**, позже — собственная БД на DigitalOcean.

Цель: сайт будет расти постепенно, блоки будут визуально меняться. Код должен оставаться понятным, легко рефакторимым и тестируемым — без огромных файлов на 500+ строк.

## 1. Структура папок

```
/src
  proxy.ts                  # определяет локаль по URL, редиректит "/" -> "/<defaultLocale>" (в Next.js 16 это "proxy", не "middleware")
  /app
    layout.tsx               # корневой layout: только <html>/<body>, шрифты
    /[locale]
      layout.tsx              # Header + обёртка страницы для конкретной локали
      page.tsx                # Главная
      /kompaniya/page.tsx
      /brendy/page.tsx
      /magaziny/page.tsx
      /novosti/page.tsx
      /journal/page.tsx
      /loyalty/page.tsx
    /api
      /revalidate/route.ts    # webhook от Storyblok на обновление контента

  /components
    /blocks                   # 1 файл = 1 Storyblok-компонент (blok)
      Hero.tsx
      TextWithImage.tsx
      CardsGrid.tsx
      ...
      index.ts                # РЕЕСТР блоков для Storyblok resolver (единственный разрешённый "большой" файл-реестр)
    /ui                        # переиспользуемые примитивы дизайн-системы, не привязаны к CMS
      Button.tsx
      Container.tsx
      Section.tsx
    /layout
      Header.tsx
      Footer.tsx
      Nav.tsx

  /lib
    /i18n
      locales.ts               # список локалей (ru_ru, ru_am, ...) + defaultLocale
    /storyblok
      client.ts               # инициализация Storyblok SDK
      fetchStory.ts            # функции получения контента по slug, с учётом locale/market
    /db                         # (появится позже, под DigitalOcean БД)
      client.ts
      queries/                 # по одному файлу на сущность: products.ts, news.ts...
    format.ts                  # хелперы форматирования (даты, цены и т.д.)
    validation.ts               # хелперы валидации форм

  /types
    storyblok.ts                # TS-типы под схемы Storyblok-компонентов

/tests
  # тесты лежат рядом с файлом: Hero.tsx + Hero.test.tsx
```

## 2. Главные правила

1. **Один компонент/блок — один файл.** Никогда не объединять два блока или два компонента в одном файле, даже маленьких.
2. **Имя файла блока = технический код (technical name) компонента в Storyblok.** Так соответствие CMS ↔ код видно сразу, без гадания.
3. **Страницы (`app/**/page.tsx`) — тонкие.** Их задача: получить данные через `lib/storyblok/fetchStory.ts` и отрендерить `<StoryblokComponent blok={...} />`. Никакой бизнес-логики и вёрстки внутри `page.tsx`.
4. **Компоненты не ходят за данными сами.** Данные приходят через props, полученные на уровне страницы. Это делает компонент чистым и легко тестируемым в изоляции (не нужен мок сети, чтобы протестировать рендер).
5. **`components/blocks` vs `components/ui`.** Блоки — это то, что описано в Storyblok и может исчезнуть/измениться по решению маркетолога. UI-примитивы — постоянная дизайн-система (кнопки, контейнеры, сетки), на них блоки опираются. Не смешивать.
6. **Реестр блоков — единственный "клеевой" файл.** `components/blocks/index.ts` — единственное место, где разрешено импортировать все блоки разом (для `storyblokEditable` / resolver). Больше нигде так делать нельзя.
7. **Лимит на размер файла — ориентир 150–200 строк.** Если компонент перерастает это — выносить подкомпоненты в папку:
   ```
   components/blocks/CardsGrid/
     index.tsx
     Card.tsx
   ```
8. **Утилиты — по доменам, не в один общий `utils.ts`.** Как только файл хелперов разрастается — делить: `format.ts`, `validation.ts`, `seo.ts` и т.д.
9. **Будущая БД (DigitalOcean) — только через `lib/db/queries/*`.** Компоненты и даже `page.tsx` никогда не обращаются к БД напрямую — только через функции доступа к данным. Это позволит потом менять БД/ORM, не трогая страницы.
10. **Состояние — по умолчанию локальное.** Не тащить Redux/Zustand заранее "про запас". Глобальный стейт-менеджер добавляем только когда появится конкретный кейс, который не решается локальным `useState`/URL-параметрами.
11. **Секреты — только через `.env`.** Storyblok-токен, позже — креды БД. Никогда не хардкодить.

## 3. Локализация и рынки (i18n)

Сайт мультиязычный и мультирегиональный: URL вида `trendsetter.com/ru_ru/...`, `trendsetter.com/ru_am/...` (по образцу H&M — `<язык>_<страна>`, всё в нижнем регистре).

- **Список локалей** — единственный источник правды: `lib/i18n/locales.ts`. Добавить новый рынок = дописать строку в массив `locales`, больше нигде хардкодить локаль нельзя.
- **Роутинг** — весь сайт живёт под `app/[locale]/...`. `src/proxy.ts` редиректит `/` на `/<defaultLocale>` и признаёт только локали из `lib/i18n/locales.ts`.
- **`app/[locale]/layout.tsx`** проверяет, что `locale` из URL входит в список известных — если нет, `notFound()`.
- **Разделение контента по рынкам (акции, новости, магазины).** Это не про перевод текста, а про то, кому вообще показывать конкретную запись: акция на джинсы в Ереване не должна попадать посетителю из Москвы. В Storyblok у таких контент-типов должно быть поле `markets` (мультиселект по датасорсу со списком рынков). Любой запрос списка (`fetchStory`/`fetchStories`) обязан фильтровать по `markets` = текущая локаль — фильтрация делается на уровне запроса к CMS, а не постфактум во фронтенде.
- **Перевод общих текстов** (шапка, футер, статичные страницы) — через встроенный `language`-параметр Storyblok API. Локаль из URL пробрасывается в каждый вызов `fetchStory`.
- Компонент никогда сам не определяет локаль/рынок — она приходит пропом сверху (`page.tsx` → компонент), как и любые другие данные (см. правило 4 выше).

## 4. Дизайн-токены (Figma)

Макет: файл **TRENDSETTER** в Figma (страницы `DRAFT`, `WEB`, `UI-KIT`). Значения снимаются со страницы `WEB` через Figma REST API — токен и ссылка лежат в `.env.local` (`FIGMA_TOKEN`, `FIGMA_FILE_URL`), файл в `.gitignore`.

- **Цвета и шрифты живут только в `app/globals.css`** — как CSS-переменные, а дальше используются через Tailwind-классы (`bg-brand`, `text-ink`, `bg-surface`). Не хардкодить hex в компонентах: смена палитры должна быть правкой одного файла.
  - `--brand: #a22325` — фирменный красный
  - `--ink: #252120` — тёмный (футер, основной текст)
  - `--surface: #f3f3f3`, `--surface-strong: #e8e8e8` — серые подложки
- **Два шрифта — файлы от дизайнера в `app/fonts/`**, подключены через `next/font/local` в `app/layout.tsx` (variable-версии, поэтому одна пара файлов покрывает все начертания):
  - `font-mono` — **Geist Mono**: заголовки секций `[...]`, бегущая строка, теги, даты, слоган;
  - `font-sans` — **Inter Tight** (по умолчанию для `body`): навигация, тексты, заголовки статей.
  - Italic-файлы лежат рядом, но не подключены — незачем грузить их, пока курсив не понадобится.
- **Логотип TRENDSETTER — вектор, а не текст.** `public/images/logo.svg`, выведен через `components/ui/Wordmark.tsx` как CSS-маска: цвет задаётся классом текста, поэтому один файл работает и красным в шапке/hero, и белым в футере.
  - «Полупрозрачность» надписи в макете — это **режимы наложения**, а не `opacity`: в hero `LINEAR_DODGE` (`mix-blend-plus-lighter`), в футере `SOFT_LIGHT` (`mix-blend-soft-light`).
- С 28.08.2026 в файле есть **библиотека компонентов** — отдельные страницы `Styles` / `Features` / `Components`. Готовые к работе помечены дизайнером зелёным кружком 🟢, красный ❗️ — его собственная пометка «не доделано», на неё не ориентируемся. Опубликованных стилей и переменных по-прежнему нет: значения снимаем со слоёв, но теперь с компонентов библиотеки, а не с экранов.
  - `Colors`, `Typography`, `Spacing`, `Grid` пока **не наши** — там шаблон чужой системы (Manrope), брать оттуда значения нельзя.
  - Кнопки уже сведены: `components/ui/Button.ts`, набор `2394:8622`.
- Выгрузка Variables через API доступна только на тарифе Enterprise — если токены заведут переменными, снимать их придётся вручную или через Dev Mode MCP.

⚠️ **Читая инстанс компонента, смотреть флаг `visible`.** Дизайнер держит в компоненте все слои сразу, а на экране гасит ненужные: у `Title` полоса слайдера и стрелки лежат рядом, но включена всегда только одна. Разбор, который печатает дерево без проверки `visible !== false`, показывает лишние элементы — так в код попали полосы прокрутки во всех секциях вместо двух. То же и с `opacity: 0`.

⚠️ **Не запрашивать у API фрейм страницы целиком.** Лимит у Figma считается по стоимости запроса, и один вызов `/v1/files/:key/nodes?ids=<фрейм страницы>` без `depth` выбивает токен в `429` надолго; ретраи в цикле только продлевают блокировку. Порядок: сначала фрейм с `depth=1`, чтобы найти id нужной секции, потом уже её одну с `depth=5..6`. Один раз уже наступили.

Альтернатива без API: в Figma правый клик по слою → *Copy/Paste as* → **Copy as CSS** даёт размеры, паддинги, gap и рамки текстом. Быстрее и не тратит лимит.

### Снятые размеры: `Subscribe Our Newsletter` (1920)

Записано, чтобы не запрашивать повторно. Секция **1920×380**, `padding: 40`, `gap: 24`, фон `#A22325` — то есть на контент остаётся 300px, и они раскладываются ровно:

`заголовок 36 + 24 + описание 72 + 24 + форма 80 + 24 + чекбоксы 40 = 300`

| Элемент | Макет | В коде |
| --- | --- | --- |
| Заголовок `[...]` | 30/36 Geist Mono | `lg:text-3xl/9` |
| Описание | 24/36 Geist Mono, ширина 995 | `lg:text-2xl/9` |
| Форма | 995×80 | `lg:h-20`, колонка `minmax(0,995px)` |
| Поле ввода | 701×80, рамка **2px**, текст по центру, без паддингов | `flex-1 border-2 text-center` |
| Кнопка | 294×80, паддинг 16, рамка 1px, фон белый, 20px / ls 3 / 500 | `lg:w-[294px] lg:text-xl tracking-[3px]` |
| Ряд чекбоксов | 455×40, gap 24 | `gap-6` |
| Квадрат чекбокса | 40×40 | `lg:h-10 lg:w-10` |
| Подпись чекбокса | 24px, отступ от квадрата 24 | `lg:text-2xl gap-6` |

Подпись и внутренний отступ чекбокса в макете напрямую не подписаны — досчитаны из ширины ряда: `40 + 24 + 144` («Для мужчин», 10 знаков × 0.6em × 24px) `+ 40 + 24 + 158 + 24 = 454` против 455 в макете.

## 5. Картинки (пока нет Storyblok)

Картинки **выгружаются из Figma через API**, вручную ничего сохранять не нужно. Порядок такой:

1. **Фото — только по `imageRef`**: собрать `imageRef` из `fills` нужных узлов, затем взять ссылки на исходники из `/v1/files/:key/images`.
   ⚠️ **Не рендерить фрейм через `/v1/images/:key`.** Figma отрисует фрейм вместе с его содержимым, и в картинку запечётся текст макета (заголовки карточек, слоган, логотип) — на сайте он будет двоиться с живым текстом. Один раз уже наступили.
2. **Векторы (логотип, смайлик) — наоборот, через `/v1/images/:key?format=svg`**: там текста нет, а вектор нужен именно отрисованным.
3. **Сжать.** Figma отдаёт исходники как есть — это многомегабайтные PNG (было 28 МБ на 14 файлов). Прогнать через `sharp`: ресайз до ~2× от максимального размера в вёрстке и `.jpeg({ quality: 82, mozjpeg: true })` — вышло 1.2 МБ без видимой потери качества.

Складываются в `public/images/<страница>/<блок>/`:

```
public/images/
  logo.svg             # логотип, общий для всех страниц
  home/
    hero.jpg           # обложка Главной (экспорт 1x - 1920px, дальше next/image сам ужимает)
    smile.svg           # смайлик в блоке подписки (вектор, не растр)
    news/1..4.jpg       # карточки "Последние новости"
    events/1..4.jpg     # карточки "Ближайшие события"
    journal/1..2.jpg    # карточки "Журнал"
    stores/1..3.jpg     # превью магазинов
```

- Папка = страница, вложенная папка = конкретный блок на этой странице. Для новой страницы — новая папка `public/images/<slug>/`.
- Класть картинку и сразу прописывать путь (`/images/<...>`) в дефолтный проп компонента (`imageSrc`/`image`) — компоненты уже принимают путь пропом, менять вёрстку не нужно.
- Рендерить через `next/image` (`fill` + `sizes`, `priority` только для картинки над сгибом), а не голый `<img>` — даёт автоматическую оптимизацию и адаптивные размеры.
- Когда подключим Storyblok — картинки уйдут в Storyblok Assets, а эта папка останется только для контента, который не редактируется через CMS (иконки, статичные фоны и т.п.).

- Тест лежит рядом с файлом: `Hero.tsx` → `Hero.test.tsx`.
- Стек: Vitest + React Testing Library (юнит/компонентные), Playwright — позже, для сквозных сценариев по ключевым страницам.

## 7. Рецепт: добавить новую страницу

1. Создать папку `app/[locale]/<slug>/page.tsx` (внутри `[locale]`, не рядом с ним).
2. Получить `locale` из `params`, получить story через `lib/storyblok/fetchStory.ts` (передав туда locale/market).
3. Отрендерить `<StoryblokComponent blok={story.content} />` — рендер конкретных блоков Storyblok сам решит, что показывать.
4. Не писать вёрстку внутри `page.tsx` — если нужен специфичный для страницы блок, он всё равно оформляется как обычный blok в `components/blocks`.

## 8. Рецепт: добавить новый блок (Storyblok component)

1. Завести компонент в Storyblok schema, задать technical name (например `cards_grid`).
2. Создать файл `components/blocks/CardsGrid.tsx` — имя в PascalCase от technical name.
3. Описать TS-тип пропсов в `types/storyblok.ts`.
4. Зарегистрировать блок в `components/blocks/index.ts`.
5. При необходимости общих элементов — брать из `components/ui`, не дублировать вёрстку.

## 9. Storyblok: схемы блоков живут в репозитории

Источник правды по структуре блоков — `storyblok/components.json`, а не пространство. Пространство считаем расходным: сейчас оно на личном аккаунте, потом переедет на корпоративный, и переезд должен быть командой, а не пересборкой схем руками.

- `npm run storyblok:push` — заливает схемы из файла в пространство. Блоки сопоставляются по имени: что есть в файле — создаётся или обновляется, что есть только в пространстве — не трогается (удалить блок значит удалить чужой контент).
- `npm run storyblok:seed` — заполняет историю `home` теми секциями, которые сайт показывает сейчас, чтобы новое пространство начиналось не с пустоты.
- Оба скрипта читают `.env.local` и требуют `STORYBLOK_PERSONAL_TOKEN` — он живёт только на машине разработчика, в Vercel не заводится.
- Картинки в личное пространство не заливаем: ассеты привязаны к пространству, при переезде их всё равно пришлось бы загружать заново. До переезда компоненты берут картинки из `public/images/`.

Чтение: `lib/storyblok/client.ts` (хост, токен, кеш, теги) и `lib/storyblok/fetchStory.ts`. Своего SDK не подключали — обычный `fetch`, поэтому в рецептах ниже вместо `StoryblokComponent` будет наш собственный реестр. `fetchStory` пока принимает только slug; locale/market появятся вместе с задачей про рынки.

Кеш: каждая история носит тег `storyblok:<slug>` и общий `storyblok`. `/api/revalidate` сбрасывает названную историю, `/api/preview` включает режим черновика для редактора.
